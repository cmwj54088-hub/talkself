## 聊天导入的事实与契约

主对话已按用户要求检查本地 `evidence/` 诊断 JSON 的结构和五个微信 ZIP 的正文行结构；没有复制私人正文进项目文件。当前原生 WechatArchive、ShareInbox、预览、编辑及备份校验均存在正文限制，不能只改单个常量。

- combine 合并样本：正文存在发送者标题、时间、消息正文边界；含图文的样本在相应消息中有媒体引用。应拆回原消息；同一人连续发两次仍是两个气泡，不能按相同用户名再次合并。消息正文内部换行／空行不等于新消息。
- one by one 逐条样本：观察到以多个 `·` 文本项分隔、没有发送者和原时间的正文；另有单条文字／单张媒体样本。不能假定与 combine 拥有相同元数据。执行者需核对诊断记录对应的 ZIP 名称、实际格式再编写解析，文件名或空行不能独自充当可靠消息边界。
- 用户希望显示用户名：来源提供的名字作为独立显示字段，不能全部显示为“我”，不能把名字仅拼进正文。来源未提供时明确显示“未知发送者”或“来源未提供”，不凭正文猜姓名，也不把接收者当原发送者；原时间缺失同样明确处理。
- 原顺序必须稳定，包括同时间消息和缺失时间消息；导入批次顺序、原发送时间和导入时间应区分。原始时间字符串可保留，未知时区不静默当作已精确解析。
- 以原发送动作作为消息单位。一条原消息包含图片／文字时保留其关联；已有图片、视频单独记录的结构若不足，需要最小兼容扩展。不要强行把一条消息附件拆成多个假发送动作。
- 不支持的结构应保留原始内容并明确提供回退／确认，不能静默吞掉消息、用错误分隔符切碎正文或声称恢复了缺失元数据。只处理用户实际交付的载荷，不读取微信私有数据库。
- 解除整个聊天的五万字硬限制，仍保留合理的字节、消息数量、附件、解压量和内存限制，并根据测试说明实际支持范围；拒绝超限时给具体原因，不静默截断。单条超长消息仍保持原消息身份，可折叠／按需显示，不因文本长度伪造多次发送。
- 大导入避免全量 DOM 预览和多份大字符串复制；沿用分块桥接、后台解析、原子存储及失败清理。不以加载动画掩盖主线程长期阻塞。
- 新增发送者／原消息时间等字段必须贯通显示、编辑、搜索所需行为、转发、导出、完整 JSON 备份恢复及旧备份兼容。若需升级 schema／备份版本，应明确迁移与兼容，不突破旧校验后又导致新备份不能恢复。

## 全屏编辑契约

- 复用实际笔记全屏编辑组件、顶栏返回／确认和内容布局，覆盖普通消息展开、待办输入展开、已有待办编辑；按模式保留必要的待办日期、时间、附件及启用提醒字段，不把不适用的正文排版工具硬塞给待办。
- 新建草稿的“发送／保存”与已有笔记的“完成编辑”语义清晰；保留共用草稿、附件、焦点和内容，返回既不隐式发送也不丢字。待办批量按行创建行为保留，每条待办对应自己的消息气泡。
- 复用已有全屏编辑器，不另建第二套难以同步的数据模型；尊重现有自动草稿、双击编辑与返回键规则。验证软键盘下顶栏／确认按钮可达，不能用桌面截图代替真机键盘验证。

## 待办消息流、历史数据与转发契约

- 首选将同项目已有 tasks 与 messages 合成展示流，按原创建时间及稳定 ID 排序，任务气泡直接引用原 task ID。历史任务自动从现有本地数据呈现，无需再次导入或安装后重新扫描外部文件，也不复制生成第二份 tasks／messages 记录。
- 如果实现确需持久化关联或迁移，必须幂等、原子、保留原 ID 和时间，并验证重复启动、失败重试及旧 JSON 恢复不重复；只有必要时才做迁移，不能无理由扫描重写所有用户数据。
- 气泡、待办栏、全局列表是同一条待办的入口。完成／取消完成同步，保持现有完成后撤销提醒、恢复未完成时依据当前提醒契约重新处理等行为，不能重复预约或擅自申请权限。
- 任务转发使用新 ID，目标项目创建独立 tasks 记录，自动在其消息流及待办栏呈现；多目标及附件存储原子写入，失败整批回滚。源任务不移动、不修改，各副本完成／编辑独立。
- 普通默认：转发为目标项目的新未完成待办，保留正文、附件和可用截止日期；不自动复制已生效的系统预约或启用提醒，避免未经用户设置即重复响铃。界面或确认摘要应说明新任务状态，若用户后续指定不同语义再更新。
- 既有任务附件、创建时间、编辑、删除、搜索定位、项目预览、统计、Markdown 与完整备份都覆盖消息流入口；派生气泡不能在备份／导出里导致同一待办被重复计数和输出。
